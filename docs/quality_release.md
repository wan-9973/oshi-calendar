# 商品品質と検索安定性の改善

## 変更内容

- 本人名義は分割した著者・出演者の完全一致で判定。英字名の単語内部分一致を禁止し、Eve/M!LKの識別設定を追加。
- サーバーレスの外部検索に45秒の共通予算を設定。HTTP接続・再試行・DBレート制御のロック待ちを制限。保存時間の余白を確保するが、異常なDB停止までの完全な実行時間保証ではない。
- 巡回の既定予算は24リクエスト。別名で24件を超える推しでも最初の1件は時間予算内で処理し、失敗・未取得の媒体をDBに保存して1時間後に再試行。再試行では当該媒体だけを全別名に対して取得する。
- IPハッシュ別の60秒・3件制限と、同じ名前の90秒検索リースをDBで共有。別名を正規名へ変換してからキャッシュを確認。
- 月別APIにoffset/next_offsetを追加し、画面・書き出しが全ページを取得。ICS UIDは推しIDと商品コードを使用し、UTF-8の75オクテット折り返しを実施。
- 月・年のみ判明、または「頃」「以降」の予定には確定日のカウントダウンを表示しない。

## 検証

```text
python -m pytest tests -q
node --test tests/calendar-client.test.cjs
node --check src/web/static/app.js
```

実データの変更・楽天APIへのリクエストを行わないモックと一時SQLiteを使用する。
本番PostgreSQLの競合・高負荷、外部API遅延時の実測、実ブラウザ/カレンダーアプリへのインポートは別途確認する。

## リリース手順

1. プレビューでトップ、推し詳細、マイ推し、カレンダーの取得を確認。
2. DB初期化で追加される `items.quality_excluded`、`crawl_queue.pending_apis_json`、`search_gates` を確認。既存列・データの削除はない。
3. 本番反映後、接続済みの運用環境で `python -m src.quality` を実行し、変更件数と先頭20件の例を確認。
4. `python -m src.quality --apply` でグッズ・雑誌・楽天市場・総合検索も含む全媒体の関連度を再計算する。表示・非表示フラグは変更せず、根拠不足の商品は「関連未確認」と表示する。過去の処理ですでに非表示だった商品も、この処理では表示状態を変更しない。巡回時にも同じ推しの全媒体を再判定する。
5. トップHTTP 200、`/api/health`、EveとM!LKの誤掲載解消、正しいCD等の保持、65件以上の月別全件取得を確認。

再判定前に items の対象行の relevance/quality_excluded を運用環境内でバックアップする。表示フラグを0に戻せば非表示を解除できる。コードの切り戻し時にも追加列/テーブルは残せる。

`CRAWL_BUDGET_PER_RUN` を環境変数で上書きしている場合は、新しい既定値より環境変数が優先される。小分け回数増加による巡回遅延は `/api/health` のキューで監視する。

## 全媒体の再判定

既存データの表示時も現在の関連度ロジックで判定し、古いスコアを「グッズ関連」等の断定に使わない。関連を確認できない商品は表示を保持し、トップ・詳細・マイ推しリスト・カレンダーAPIで同じ「関連未確認」と対象名を説明する。関係性フィルタにも未確認区分を追加する。

新規取得時の商品説明を `items.caption` に保存する。既存データの空の説明文は「関連なし」の証明とは扱わず、確認できる根拠が不足していることを表示する。説明文だけの一致も本人名義にはしない。新規検索時の候補取得フィルタは維持する。
